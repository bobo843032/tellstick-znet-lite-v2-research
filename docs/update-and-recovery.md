# Firmware update and recovery paths in 1.3.2

This analysis uses the official ZNet Lite V2 1.3.2 image identified in [references](references.md). The paths below are from the extracted image; they have not been exercised on a gateway. The [offline verifier test](../tests/test_stock_upgrade_verification.py) runs the original Python verifier with synthetic data and a substituted GPG subprocess. It does not test an actual vendor signature or write flash.

## Vendor update path

`/etc/init.d/telldus-upgrade` starts `/usr/bin/tellstick-upgrade.sh` through procd. The shell script checks hotfixes and versions, stops `telldus-server` before an upgrade, and restarts it if the download fails. In `tellstick-upgrade.py`, `UpgradeManager.check()` reads the version catalogue over HTTP; `download()` requires a declared size and SHA-1, fetches the image and a detached `.asc` file, and calls `UpgradeManagerBase.verifyFile()`. That verifier rejects size or SHA-1 mismatches and rejects a nonzero `gpg --verify` result against `/etc/upgrade/telldus.gpg` before `Board.doUpgradeImage()` is called. Four tests of these branches passed with original Python code and mocked GPG return values. **A modified image is not accepted by this vendor-managed path merely because it has the right filename or header.** This study has not verified a vendor signature and has no signing key.

For this board, `board.Board.doUpgradeImage()` delegates firmware installation to `/sbin/sysupgrade`. The stock `lib/ar71xx.sh` maps the board to `tellstick-znet-lite-v2`; `lib/upgrade/platform.sh` places it in the TP-Link-style image-check branch, requiring image magic, matching hardware/model IDs, and no bootloader in the image. The official 1.3.2 file starts with `01000000`; its inspected header has hardware ID `00726101`, model ID `00000001`, and zero bootloader size at the offsets read by that branch. These are **format observations**, not an installation test or an independent authenticity guarantee. The manual `sysupgrade` script has image-format checks but no GPG check in its examined path; the vendor downloader performs the signature check before invoking it. This distinction does not establish that a custom image is safe to install or recover.

The `firmware` MTD region overlaps `kernel` and `rootfs`; the documented flash map has one firmware region rather than a verified redundant A/B slot. `lib/upgrade/common.sh:default_do_upgrade()` writes an image to the selected MTD partition and optionally embeds a configuration archive. An interrupted write can therefore require an independent recovery path. The observed U-Boot command list includes an HTTP recovery command, but accepted images, validation, access procedure, and the ability to restore the current unit have **not** been tested. Neither a bootloader command nor a private flash dump alone proves recoverability.

The inspected `/sbin/sysupgrade` accepts a local image path, so the Linux-side code has a cloud-independent input route for an official image when an authorized root shell and a working system are available. Its board checks and write path are only statically traced here. A local-image route is not a proven recovery method for a device that no longer boots, and no full reflash should be attempted without a separately tested serial/bootloader path and verified device-specific backups.

## Overlay persistence and ordinary upgrades

The stock SquashFS root and JFFS2 overlay allow a possible non-flashing integration. `usr/bin/tellstick-znet.py` imports plugin classes by module name, and `/etc/init.d/telldus-server` starts that script through procd. The existing offline draft would shadow only this startup script and add a local plugin and HTTPS server class. Earlier research documented bidirectional UART and the owner reports a root shell and SSH login during that session; the currently available records do not verify present access or a writable overlay. The draft still needs device-specific checks for writable space, package import precedence, process permissions, TLS, firewall reachability, and rollback.

The ordinary configuration-preservation list in `/etc/sysupgrade.conf` contains `/etc/Telldus.conf`, `/etc/telldus/`, Lua scripts, and `/usr/lib/telldus/plugins/`. It does **not** list a shadow of `/usr/bin/tellstick-znet.py` or the prototype's Python package path under `site-packages`. The default `sysupgrade` path saves selected configuration files, not every overlay change. Consequently, the proposed patch cannot be assumed to survive a firmware upgrade. Automatic hotfixes may also write individual target files and run signed scripts; their interaction with a local overlay requires version-by-version review.

The V2 runs on a MIPS 24Kc/AR933x board with 16 MB SPI flash, 64 MB RAM, and two USB CDC ACM radio interfaces observed in the earlier hardware study. [OpenWrt's ath79 target](https://openwrt.org/docs/techref/targets/ath79) succeeded ar71xx, but a supported current image for this **specific board** and compatibility with its RF433/Z-Wave controller protocols have not been established. A new operating-system image would require board support, storage budgeting, USB/radio integration, configuration migration, and a proven recovery procedure; it is a separate engineering project, not a direct replacement for the tested plugin.

## Recovery gates before any write

1. Confirm the exact device, firmware revision, MTD map, overlay mount and free space, startup owner, and current update behavior through authorized read-only access.
2. Establish and test an independent administrative/recovery channel before relying on an overlay rollback. Do not infer present access from an older UART study.
3. Make encrypted, readable, checksummed backups of the files that would be shadowed, overlay contents, Telldus configuration, and any Z-Wave controller state that can actually be exported. Controller NVM may be separate from filesystem settings.
4. Review TLS certificate trust, firewall scope, and all existing HTTP paths. A local owner password must never be sent over unprotected stock HTTP.
5. Stage a version-specific, removable overlay only after those checks. Verify stock startup/API and known nodes after a rehearsed rollback. Review persistence again before every vendor upgrade.

**Decision:** an in-process overlay is the smallest plausible route for a first controlled test. Full firmware replacement is not required by the demonstrated authentication flow. Device deployment and flash replacement remain **NO-GO** until the recovery and transport gates have been verified on the actual gateway.
