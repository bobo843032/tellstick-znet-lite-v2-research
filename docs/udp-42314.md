# UDP 42314 in stock firmware 1.3.2

This document follows the extracted 1.3.2 Python 2.7 bytecode. Module names below are the embedded firmware paths; line numbers refer to a private decompiled reading copy and are approximate. The [published regression test](../tests/test_udp42314_original_offline.py) executes original modules under MIPS emulation with fake sockets. A separate non-published test also exercised the real RF433 encoder against a mock queue. **Later physical follow-up:** a targeted registration datagram reached an owned gateway and received a Z-Wave version notice; no RF command or sensor packet was transmitted by these tests.

## Startup and transport

`/usr/bin/tellstick-znet.py` registers `productiontest.Server` among the application's startup plugins. `productiontest/Server.py:Server.__init__` (about lines 80–91) creates ordinary `SocketServer.UDPServer` listeners bound to `0.0.0.0` on UDP 30303 and 42314, then starts one serving thread for each. UDP 42314 is handled by `CommandHandler`; the RF433 serial adapter has its own worker thread. This is a single-request-at-a-time UDP server, not a per-client session service.

The stock `/etc/firewall.telldus` adds accept rules for both UDP ports in `input_wan_rule`. This is a **STATIC CODE VERIFIED** firewall configuration, not a measurement of internet reachability. Local reachability was later tested on the owned gateway. No authenticated handshake, sender address allowlist, token check, or per-client registration limit appears in the 42314 handler. A network boundary is therefore necessary for safe local use; the port must not be treated as an authenticated API.

## Messages and dispatch

The handler strips the incoming datagram, checks one exact listener-registration value, and then parses the same data with `tellduslive.base.LiveMessage.fromByteArray`. `LiveMessageToken.parseToken` (about lines 82–165) handles length-prefixed strings, integers, lists, dictionaries, and a Unicode/base64 variant. The first token becomes a lowercased message name; later tokens become arguments. The 42314 handler recognizes only a listener registration and the `send` name. Other names have no handler in this module. This framing is also used elsewhere in the firmware, but 42314 does **not** call the `LiveMessage` signature-verification method.

| Direction | Firmware path | Observed role |
| --- | --- | --- |
| Client to gateway | `CommandHandler.handle`, about lines 48–57 | Replace the one registered event recipient, or dispatch `send` to the RF433 path |
| Gateway to recipient | `Server.rf433RawData`, about lines 100–110 | Forward RF433 event data as `RawData` after converting a hex field to an integer |
| Gateway to recipient | `Server.sendVersion`, about lines 113–130 | Send a `zwaveinfo` controller-version notice when available |

Listener registration saves the UDP request socket and sender IP:port in `Server.listener` and `Server.clientAddress`. A later registration simply replaces both. There is no expiry, explicit unregister, ownership check, or multi-subscriber list in this module. The address remains until replacement or process termination; failed event sends are caught and silently discarded. Two integrations that independently register can therefore displace each other. The original-bytecode mock test verified replacement with two distinct loopback addresses; it did not test a live third-party client.

## RF433 command and event paths

For `send`, `CommandHandler.handleSend` (about lines 59–73) selects a `rf433.Protocol` encoder, sets model and selected device parameters, encodes the requested method, and places an `RF433Msg` in `RF433.dev.queue`. `rf433/Adapter.py:queue` (about lines 37–41) wakes its serial worker; `Adapter.run` (about lines 43–91) opens the RF433 serial port, writes queued messages, and waits up to five seconds for a matching controller response. The 42314 path supplies no completion callback and sends no application acknowledgement to the UDP client. A successful handler return means at most that data was queued, not that RF transmission or device state was confirmed.

The UDP handler does not expose all parameters available to the normal `RF433` device-command path; protocol instantiation alone does not prove transmission support for every model or method. The private original-bytecode test confirmed that one supported synthetic encode request reached a fake adapter queue, with **no serial device**. It intentionally does not publish a reusable radio-control datagram.

For incoming RF433 data, `rf433/Adapter.py` parses serial messages and schedules `RF433.decodeData`; `RF433.decode` emits the `rf433RawData` signal observed by `productiontest.Server`. The event is already processed by the MCU/application path; its name does not imply unmodified radio samples. The server forwards it to the one registered recipient. The physical listener/version response was verified later, but RF433 event reception, supported models, event completeness, and state synchronization remain unverified. A later temporary sensor observer received only a clearly simulated `sensorValueUpdated` callback in the daemon, not a physical RF433 report.

## Input handling and stability

The original parser accepts some incomplete length declarations instead of rejecting the entire message. A `send` message without its expected dictionary raises an exception in `handleSend`; malformed fields can also raise before any RF queueing. An invalid hexadecimal event value raises in `rf433RawData` **before** its `sendto` exception handler. The handler does not set a datagram-size limit, application-level rate limit, or queue bound in the examined path. These are code-path findings, not measured denial-of-service results.

**VERIFIED IN EMULATION ONLY:** Nine private original-module tests passed: parser roundtrip, lax malformed parsing, registration/replacement, inert unknown message, incomplete-send exception, a real encoder with mock adapter, RF433 event forwarding/bad-hex handling, outbound Z-Wave version notice, and a loopback UDP server that continued to handle registration after a malformed request. The [seven public tests](../tests/test_udp42314_original_offline.py) omit the operational encoding example and network probe. **RUNTIME VERIFIED follow-up:** targeted registration on the owned gateway returned a version notice, and registration still answered after one incomplete message. Sustained malformed traffic and physical RF delivery were not tested.

## Relationship to UDP 30303 and Z-Wave

| Property | UDP 30303 | UDP 42314 |
| --- | --- | --- |
| Purpose in stock code | Discovery response | RF433 command and event-recipient service |
| Information leaving the gateway | Discovery identity and device-specific sensitive material | RF433 event data and a Z-Wave **version** notice to the registered recipient |
| Inbound local control | None in the examined handler | RF433 encode/queue path; **no inbound Z-Wave command path** in this handler |
| Authentication in handler | None observed | None observed |
| Integration impact | Sensitive discovery response; do not expose to untrusted networks | Single listener can be replaced; no delivery acknowledgement |

`Server` instantiates `TelldusZWave` and can send its controller-version notice, but `CommandHandler.handle` dispatches no Z-Wave control message. Z-Wave administration remains in other application/Live code paths; this UDP port is not a substitute for a local Z-Wave management API. A successful 42314 RF433 test would not establish Z-Wave operation.

## Local Home Assistant use and attribution

UDP 42314 is a plausible local RF433 event/control transport **without JWT or Telldus Live token approval** in the examined handler. A Home Assistant adapter must account for one listener, loss/re-registration, untrusted senders, lack of command acknowledgements, and the difference between an encoded command and an observed device state. The existing [R00S local integration](references.md) already implements a 42314-based approach for supported devices. Reuse or coordinate with that integration before introducing another listener. For read access and controlled device actions beyond this UDP subset, the [stock HTTP API](interfaces.md) plus the [local-owner prototype](authentication.md) is the stronger architectural basis. Full no-cloud Z-Wave administration needs additional scoped local routes and hardware tests.

The earlier [ob-wn issue #1](https://github.com/bobo843032/tellstick-znet-lite-v2-research/issues/1) specifically identified the unauthenticated **30303** discovery/secret exposure and linked the [ob-wn no-cloud project](https://github.com/ob-wn/tellstick-znet-lite-v2-nocloud). That lead prompted our targeted firmware study. ob-wn's project and R00S's integration also discuss local 42314 use; this document claims the tested code-path details and limits, not first discovery of that port. The wider hardware and firmware investigation predates the issue.
