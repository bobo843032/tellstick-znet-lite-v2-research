RF433 Subsystem — Hardware, USB Interface and Protocol Analysis

Overview

The Telldus TellStick ZNet Lite V2 contains a dedicated 433 MHz radio subsystem used to communicate with compatible wireless home automation devices.

Unlike the gateway’s integrated Wi-Fi interface, the RF433 subsystem is not controlled directly by the Atheros Linux processor. Instead, it uses a separate Microchip microcontroller connected to a Maxim radio transceiver.

The Linux application communicates with this subsystem through an internal USB CDC ACM serial interface.

This document describes the identified hardware, USB architecture, application-level protocol processing and the limitations of the available RF data.

Research was performed on personally owned hardware running stock firmware version 1.3.2.

A key finding is that the Linux application receives structured radio messages rather than unrestricted raw RF waveform samples.

3. Maxim MAX7030 Transceiver

The Maxim MAX7030 is a radio transceiver designed for amplitude-based digital radio communication.

The device is associated with the TellStick’s 433 MHz functionality.

Relevant Characteristics

The component supports ASK/OOK radio operation, which is commonly used by simple wireless sensors, remote controls and home automation transmitters.

In ASK/OOK systems, information is represented through changes in carrier amplitude.

On-off keying is a form of amplitude-shift keying in which the carrier is switched between active and inactive states.

What the Hardware Identification Establishes

The presence of the MAX7030 establishes that the RF433 subsystem uses dedicated radio hardware suitable for ASK/OOK communication.

It does not, by itself, establish:

* Every supported radio protocol
* The complete range of operating frequencies
* Available modulation configurations in the installed firmware
* Whether raw pulse timing is accessible through USB
* Whether arbitrary radio transmissions can be generated
* The exact radio-control signals used by the PIC

Those capabilities depend on the surrounding circuitry and microcontroller firmware.

4. Microchip PIC18F25K50

The PIC18F25K50 is a USB-capable microcontroller associated with the RF433 subsystem.

It provides a separate processing layer between the Linux host and the radio transceiver.

Observed Role

The Linux host communicates with the RF433 subsystem through the PIC’s USB interface.

The MCU participates in the radio subsystem’s control and communication path.

Its exact internal processing has not been fully established through firmware disassembly.

Potential Responsibilities

Based on the observed architecture, the microcontroller may perform functions such as:

* Radio initialization
* Receive and transmit control
* Signal timing
* Message framing
* Filtering of received events
* Communication with the Linux host

These are potential responsibilities, not a verified list of implemented firmware functions.

The division of processing between the PIC and the Telldus Python application remains an important subject for further research.

5. Internal USB Interface

The RF433 controller is connected to the Linux host through an internal USB hub.

Original Kernel Log

[   11.844816] cdc_acm 1-1.4:1.0: ttyACM1: USB ACM device

The first interface is associated with the RF433 subsystem.

The second interface belongs to the separate Z-Wave controller.

RF433 USB Identification

Vendor ID:  1781
Product ID: 0c32

The operating system exposes the RF433 controller as:

/dev/ttyACM0

The device uses the Linux cdc_acm driver.

This allows the gateway application to communicate with the controller through a serial-style device interface.

Important Distinction

A USB CDC ACM interface provides a transport for messages.

It does not establish that the data carried over that transport consists of raw radio samples.

The format and meaning of the data are determined by the firmware and application protocol.

7. Serial Message Format

Inspection of the application protocol revealed structured serial messages.

Observed messages use a leading + character and contain fields representing decoded information.

A schematic representation is:

+W...<field>:<value>;...

This is an illustrative format description, not a verbatim captured RF433 message.

The exact field names and supported message types depend on the controller firmware and Telldus protocol implementation.

Interpretation

The existence of structured fields indicates that the Linux application receives data that has already been framed or processed.

This differs from direct access to a sequence of raw RF pulses.

The available evidence does not establish whether additional unprocessed information can be obtained through undocumented MCU commands.

8. Understanding rf433RawData

One particularly important finding concerns the application event named:

rf433RawData

The name may suggest that the event exposes raw radio data.

However, examination of the relevant software path showed that the event is emitted after parts of the incoming message have already been processed.

Observed Application Behavior

The RF433 implementation uses a decode method associated with:

RF433.decode

The signal:

rf433RawData

is emitted after processing within the decode path.

Simplified Processing Sequence

Incoming serial message
         |
         v
RF433.decode
         |
         +-- Parse incoming message
         |
         +-- Interpret fields
         |
         +-- Process protocol information
         |
         +-- Emit rf433RawData

The exact internal function sequence may contain additional operations not represented in this simplified diagram.

Why This Matters

An event emitted after parsing cannot automatically be treated as an unmodified record of everything received by the radio.

If decoding fails before the event is emitted, the application may never expose that particular input through rf433RawData.

This creates an important distinction between:

1. Raw RF signals received by the transceiver
2. Data processed by the microcontroller
3. Serial messages delivered to Linux
4. Messages successfully processed by the Python decoder
5. Events exposed to application listeners

These layers should not be described as equivalent.

9. Decode Errors and Visibility

The location of an application event within the processing pipeline affects what researchers can observe.

If an incoming message causes a decoding exception before an event is emitted, that event may not be generated.

Consequently, monitoring only rf433RawData may omit malformed, unsupported or otherwise unrecognized messages.

This does not establish whether the missing messages were discarded by the PIC firmware or rejected later by the Python application.

Determining that requires observation at an earlier point in the processing path.

Research Implication

For protocol analysis, it is useful to distinguish between:

* Data delivered by the USB serial interface
* Data accepted by the application parser
* Data emitted as an application event

Observing these stages separately can help identify where information is filtered, transformed or lost.

11. Relationship to Z-Wave

The two subsystems should not be confused.

Although both systems use internal USB serial communication, their radio hardware and software protocols are distinct.

12. Read-Only Inspection Commands

The following commands can help inspect the RF433 interface on an authorized device.

Confirm Device Presence

ls -l /dev/ttyACM0

Inspect USB Enumeration

dmesg | grep -i -E 'usb|cdc_acm|ttyACM'

Inspect USB Device Information

cat /sys/class/tty/ttyACM0/device/uevent

Identify Processes Using the Interface

Where supported by the installed userspace:

fuser /dev/ttyACM0

The stock Telldus application may already have the device open.

Opening the same serial interface from multiple processes can interfere with application communication or consume data intended for the original process.

These inspection commands do not intentionally modify controller firmware or transmit radio signals.

13. Areas for Further Investigation

13.1 PIC Firmware Analysis

A deeper investigation of the PIC18F25K50 firmware could clarify:

* Radio initialization
* Receive filtering
* Message framing
* Transmit timing
* Protocol handling
* USB command implementation

The feasibility of firmware extraction depends on the microcontroller configuration and any applicable code-protection settings.

13.2 Electrical Signal Mapping

Tracing the physical connections between the PIC and MAX7030 could establish:

* Data signal routing
* Transmit and receive control
* Clock and timing signals
* Radio configuration interfaces
* Available debug or test points

No complete electrical mapping has been published.

13.3 USB Protocol Documentation

Further observation of the host-to-controller interface could help identify:

* Message framing
* Supported command categories
* Error responses
* Controller status reporting
* Initialization sequences

Any published protocol examples should be based on captured evidence rather than invented responses.

13.4 Receive Pipeline Instrumentation

Observing incoming serial data before application decoding would help determine whether messages are discarded or transformed before reaching application events.

This could clarify the actual meaning and limitations of rf433RawData.

13.5 Protocol Compatibility

The controller’s supported RF protocols could be documented through controlled tests with personally owned devices.

Such testing should distinguish between protocols handled by the PIC firmware and those decoded by the Linux application.

15. Research Significance

The RF433 subsystem is more sophisticated than a radio transceiver connected directly to the Linux processor.

The separate PIC18F25K50 introduces an additional processing layer between the physical radio and the gateway application.

This architecture matters when investigating unsupported devices, protocol compatibility and the limits of software-level radio monitoring.

The rf433RawData event is particularly important because its name can be misleading without understanding where it is emitted in the processing pipeline.

The evidence supports a distinction between application-visible decoded data and genuinely unprocessed radio information.

Further work on the PIC firmware and USB communication protocol may reveal additional details about the subsystem’s capabilities.

Conclusion

The TellStick ZNet Lite V2 RF433 subsystem consists of a Maxim MAX7030 transceiver, a Microchip PIC18F25K50 microcontroller and an internal USB CDC ACM connection to the Linux host.

The installed application communicates with this subsystem through /dev/ttyACM0 and processes structured serial messages.

The software exposes RF433 events and higher-level transmit functionality, but the available evidence does not establish unrestricted raw RF capture or arbitrary waveform transmission.

The most important architectural finding is the separation between physical radio reception, microcontroller processing, serial communication and application-level decoding.

Understanding those boundaries is essential for accurate reverse engineering of the RF433 implementation.
